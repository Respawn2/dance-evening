# Архитектурные диаграммы

Все диаграммы — текст в формате Mermaid. Отрисовываются GitHub при просмотре
файла. Проверяются конвейером: диаграмма, которая не отрисовывается,
не проходит (задание «Диаграммы», состав — в [../pipeline.md](../pipeline.md)).

## Что здесь есть

| Файл | Что показывает | Для кого | На какой вопрос отвечает |
| --- | --- | --- | --- |
| [`c4/context.mmd`](./c4/context.mmd) | Система, пользователи, внешние системы | Новый человек, заказчик | С чем система граничит и кто ею пользуется? |
| [`c4/container.mmd`](./c4/container.mmd) | Запускаемые части и хранилища | Разработчик, эксплуатация | Из чего система состоит и на чём сделана? |
| [`sequence/create-registration.mmd`](./sequence/create-registration.mmd) | Сценарий записи на вечер, включая отказы | Разработчик сценария | Что в каком порядке вызывается? |
| [`data/model.mmd`](./data/model.mmd) | Сущности, атрибуты, связи, ключи | Тот, кто пишет миграции (ЛР 4А) | Как устроены данные? |

Карта ограниченных контекстов предметной области лежит отдельно —
в [`../domain/context-map.mmd`](../domain/context-map.mmd): это модель правил,
а не архитектура.

## Чего здесь нет и почему

| Чего нет | Почему |
| --- | --- |
| Уровень компонентов C4 | Компонентов пока мало, диаграмма повторила бы структуру каталогов |
| Уровень кода C4 | Устаревает быстрее, чем пишется; заменяется чтением кода |
| Диаграмма развёртывания | ЛР 6Б |
| Отдельные службы для контекстов | `ADR-0003`: модульный монолит — контексты «Вечера и записи», «Отзывы» и «Учёт участников» живут модулями внутри одного контейнера сервиса API |

## Как обновлять

Диаграмма правится **в том же запросе на слияние**, который меняет систему.
Правило проверяется на саморевью по DoD: изменение, добавляющее службу
в `compose.yaml` без правки `c4/container.mmd`, не принимается.

Локальная проверка перед коммитом:

```bash
npx --yes @mermaid-js/mermaid-cli -i docs/architecture/c4/context.mmd -o /tmp/context.svg
```

## Соглашение об оформлении C4

C4 рисуется через `flowchart`, потому что встроенная поддержка `C4Context`
в Mermaid неустойчива между версиями. Классы стилей:

| Класс | Что обозначает | Цвет |
| --- | --- | --- |
| `actor` | Человек или роль | голубой |
| `sys` | Наша система или её часть | оранжевый |
| `store` | Хранилище данных | зелёный |
| `ext` | Внешняя система | серый |

Элементы, которых ещё нет, помечаются в подписи номером работы: `<b>ЛР 6А</b>`.
«Появится позже» — состояние элемента, а не его вид: кеш остаётся хранилищем
и до появления.

## Результат сверки

Пять сверок из шага 7 части 2Г; расхождения устранены или помечены.

| Сверка | Результат |
| --- | --- |
| Контекст ↔ контейнеры | Расхождений нет: лица и внешние системы совпадают, новых на контейнерах не появилось |
| Контейнеры ↔ последовательность | Расхождений нет: участники — браузерное приложение, сервис API, база данных |
| Последовательность ↔ критерии приёмки | Ветви `AC-04.1`, `AC-04.2`, `AC-04.4`, `AC-04.5`, `AC-04.6` отображены; `AC-04.3` (двое на последнее место) — не ветвь одного пользователя: состязание запросов, защита в базе (ЛР 4А), помечено |
| Контейнеры ↔ решения | `api` — `ADR-0002`, `ADR-0003`; `worker` и `broker` — `ADR-0003` (отдельный процесс, не микросервис); `cache` — `ADR-0005`; `web` — работа 8 по плану курса |
| Модель данных ↔ требования | Все сущности нужны требованиям (`USERS` — роли `NFR-02`; `EVENINGS` — `FR-01`–`FR-03`; `REGISTRATIONS` — `FR-04`–`FR-08`; `REVIEWS` — `FR-09`). Находка: `FR-13` (фотоотчёты, Should) не имеет сущности — медиа-хранилище появится вместе с реализацией в ЛР 6А, помечено в матрице |
| Ресурсы ↔ требования | Каждое `Must`/`Should`-требование имеет операцию, кроме `FR-10` и `FR-11` — асинхронные уведомления, доставка через брокер (ЛР 6А); `FR-07` без отдельной операции — цена вычисляется в ответе страницы; `FR-14` — параметр операции афиши |
