# Процесс — «Вечера»

## Команда

| Участник | Зоны ответственности | Контакт |
| --- | --- | --- |
| <ФИО> | Требования и продукт · Репозиторий и процесс · Качество · Инфраструктура | @ник |

Работаю один. По методичке один участник может держать несколько зон; все четыре
зоны покрыты. Зоны здесь — не разделение труда, а чек-лист: ни одна не должна
повиснуть. Состав зафиксирован <дата> и не меняется до конца курса.

## Подход

По методичке (раздел про выбор подхода): команда из одного человека за одним
столом — полный фреймворк не нужен, формализация создаст расходы без пользы.
Использую облегчённый процесс: непрерывный поток задач (Kanban) с недельными
контрольными точками. Спринты и церемонии не внедряю.

## Ритм

| Событие | Когда | Длительность | Формат |
| --- | --- | --- | --- |
| Фикс-час | раз в неделю | 30–60 мин | Сверка с ганттом, обновление бэклога, запись в журнал, план недели |
| Ретроспектива | раз в две недели, внутри фикс-часа | 15 мин | Что работало / что мешало / одно изменение процесса |

## Принятие решений

- Все решения по продукту и архитектуре фиксируются письменно (с модуля 05 —
  в формате записи об архитектурном решении, [adr/](adr/))
- Правило соло: любое сомнительное решение записывать с рассмотренной
  альтернативой и причиной, по которой отказался — иначе через месяц
  не вспомню, почему сделано именно так

## Ветвление и слияние

main — единственная долгоживущая ветка, всегда зелёная. Работа идёт в коротких
ветках от свежего main: `feature/…`, `docs/…`, `ci/…`, `fix/…`. Слияние — только
через pull request со squash merge: одна задача — один коммит в истории. Ветка
удаляется после слияния, прямые пуши в main закрыты защитой ветки. Сообщения
коммитов — Conventional Commits (`feat:`, `fix:`, `docs:`, `ci:`, `refactor:`,
`test:`): тип изменения виден в истории без открытия diff. Состав проверок,
локальный запуск и настройка защиты — в [docs/pipeline.md](pipeline.md).

## Определение готовности (DoR)

Задачу можно брать в работу, если:

- [ ] есть критерии приёмки в формате Дано — Когда — Тогда
- [ ] указано, какой истории из карты она соответствует
- [ ] понятно, каким изменением в интерфейсе или API проявится
- [ ] нет открытых вопросов к формулировке
- [ ] задача помещается в одну неделю; если нет — разбита

## Определение завершённости (DoD)

Задача считается сделанной, если:

- [ ] код влит в основную ветку через pull request
- [ ] проведено самостоятельное ревью: diff перечитан до слияния, все замечания линтера устранены
- [ ] конвейер проверок зелёный (состав — в docs/pipeline.md, растёт с М03)
- [ ] написаны тесты на критерии приёмки, они проходят
- [ ] документация обновлена (README или docs/)
- [ ] добавлена запись в CHANGELOG.md
- [ ] изменение проверено на чистом окружении, а не только «у меня работает»

⚠️ Ревью второго участника недоступно — команда из одного человека. Компенсация:
саморевью с перерывом (не сливать сразу после написания), строгий линтер,
обязательный конвейер, проверка на чистом окружении. Вариант согласован
с преподавателем <дата>.

Проверка формулировки по методичке: работу должен принять человек, не
участвовавший в её обсуждении. В одиночном проекте этот человек — «я через
месяц».

## Инструменты

| Документы | Markdown в docs/ | обязательно по методичке |

## Использование AI-инструментов

Упражнения методички выполнены накопительно: ЛР 2 (части 2А–2Г), затем ЛР 3
(модули 07–08); что модель предложила, что принято и что отвергнуто:

| Часть | Упражнение | Итог |
| --- | --- | --- |
| 2А | Граничные случаи для `FR-04` | Предложено 10, принято 6, отвергнуто 4: модель не различает критерий приёмки и техническую гарантию («двое на последнее место» — защита в базе, не поведение для пользователя). Разбор — в [requirements.md](requirements.md) |
| 2Б | Контексты по списку событий | Модель разделила по сущностям: «пользователи», «вечера», «записи» — типичная ошибка из методички; «лимит не исчерпан» назвала инвариантом — на деле правило сценария. Наши границы — по значению слов, [domain/event-storming.md](domain/event-storming.md) |
| 2В | Выбор архитектурного стиля | С полным контекстом (один участник, семестр, Compose) модель выбрала монолит и назвала цену; без контекста («стоит ли микросервисы?») — начинала с достоинств микросервисов. Разница подтверждает: контекст в запросе важнее формулировки |
| 2Г | Диаграмма контейнеров по описанию | Модель добавила «API-шлюз» и «CDN», которых в системе нет, и оставила часть связей без подписи: правдоподобное ≠ наше. Сравнение — в [architecture/README.md](architecture/README.md), раздел сверки |
| М07 | `Dockerfile` для FastAPI-проекта | Из отличий черновика от эталона приняты порядок слоёв и `--frozen`; отвергнуто: `pip install` без зафиксированных версий и запуск от `root` — «работает у меня» перестаёт работать в конвейере. Границы `extra="forbid"` модель объяснила верно |
| М08 | Рефакторинг заготовки целиком | Модель не ввела шов времени (`datetime.now()` остался на месте), предложила `Notifier` на четыре метода и `RegistrationManager`. Приняты имена тестов и `ids` параметризации. Полный разбор — в [refactoring-notes.md](refactoring-notes.md) |

Правило на остаток курса: модель получает контекст (требования, ограничения,
состав) и черновик; решения, числа и приоритеты остаются за человеком — их
объяснять на приёме.
