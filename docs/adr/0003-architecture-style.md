# 3. Модульный монолит с гексагональным устройством

- **Статус**: принято
- **Дата**: 2026-11-07
- **Участники**: вся команда (1 человек)

## Контекст

Нужно решить, как система организована в целом: одно приложение или несколько
служб, и как устроено внутри. Решение определяет развёртывание, способ
тестирования, устройство кода и объём работ по эксплуатации.

Решение принимается до кода. Известно: три ограниченных контекста
(«Вечера и записи», «Отзывы и репутация», «Учёт участников») и узел
уведомлений общего назначения с предложением выразить контексты модулями
(ЛР 2Б); в системе будут сервис API и база данных (ЛР 3, 4), обработчик
событий (ЛР 6А) и браузерное приложение (ЛР 8).

## Движущие факторы

- `C-04`: команда из одного человека, один семестр
- `NFR-05`: прогон тестов не дольше 60 секунд; установка на чистой машине
  не более пяти команд
- `C-05`: развёртывание через Compose, оркестрация не применяется
- `NFR-04`: вечера, записи и отзывы сохраняются при перезапуске —
  согласованность данных проще обеспечить одной базой
- Проверяемость предметной логики без внешних средств — нужна с первой
  строки кода (ЛР 3Б), иначе тесты будут требовать базы и сети
- Предложение о структуре кода из ЛР 2Б: контексты — модули внутри слоя
  предметной области

## Рассмотренные варианты

| Вариант | За | Против |
| --- | --- | --- |
| **Модульный монолит, внутри гексагональное устройство** | Одно развёртывание; согласованность данных в одной транзакции; предметная логика проверяется без внешних средств; границы модулей готовят возможное разделение | Границы поддерживаются дисциплиной и проверкой, а не техническим барьером: их можно нарушить одним импортом |
| Монолит без явных границ | Меньше файлов; быстрее писать | Через два месяца границы размываются; предметная логика перестаёт проверяться без базы и сети |
| Микросервисы: служба вечеров, служба отзывов, служба уведомлений | Независимые выпуски; независимое масштабирование | Три конвейера, три набора наблюдаемости, согласованность между базами, распределённые отказы. При `C-04` неисполнимо |
| Монолит плюс бессерверные функции для уведомлений | Уведомления масштабируются сами | Внешняя платформа — против `C-06`; локальная разработка усложняется |

## Решение

**Модульный монолит с гексагональным устройством внутри.** Одно приложение,
одна база данных, явные границы между предметной областью, интерфейсами
и адаптерами. Обработчик событий из ЛР 6А — отдельный процесс того же
приложения и той же базы: это разделение по способу запуска, а не по данным,
и микросервисной систему не делает.

**Определяющий довод** — `C-04`. Независимость служб, за которую платят
распределёнными отказами, при одном участнике не даёт ничего: выпускать
независимо нечего и некому.

Границы поддерживаются двумя средствами:

- `src/domain/` (подпакеты `evenings/`, `reviews/`, `accounts/`) и
  `src/services/` не импортируют каркас, драйвер базы и клиент HTTP; обмен
  между контекстами — только через идентификаторы (ЛР 2Б)
- правило проверяется конвейером с появлением кода (ЛР 3Б, задание
  `boundaries`): `grep -r "fastapi\|asyncpg" src/domain src/services` должен
  давать пустой результат

## Последствия

**Положительные.** Одно развёртывание, одна база, согласованность
в транзакции. Предметная логика проверяется без внешних средств — набор
тестов остаётся быстрым (`NFR-05`). Границы модулей дают путь к разделению,
если оно когда-нибудь понадобится.

**Отрицательные.** Все части выпускаются вместе: ошибка в отзывах
останавливает выпуск остальных частей. Масштабирование — только целым
приложением. Границы обеспечены проверкой, которую можно обойти
или отключить. В одиночном проекте некому заметить обход — правило
охраняется конвейером, а не только ревью.

**Что пересмотрит решение.** Появление второго участника, работающего над
системой независимо; требование разной частоты выпуска для разных частей;
нагрузка, при которой отзывы или уведомления требуют в разы больше ресурсов,
чем вечера и записи.
