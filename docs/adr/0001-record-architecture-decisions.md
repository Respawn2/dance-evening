# 1. Мы ведём записи об архитектурных решениях

- **Статус**: принято
- **Дата**: 2026-11-07
- **Участники**: вся команда (1 человек)

## Контекст

Решения о структуре системы принимаются в разговоре с самим собой и
не фиксируются. Через месяц причина решения не воспроизводится никем, включая
автора. Это уже наблюдалось: почему соприкасающиеся интервалы вечеров
не считаются пересечением, пришлось восстанавливать по критерию `AC-03.6`,
и только потому, что он попал в требования. Код ещё не написан — решения,
не записанные сейчас, придётся восстанавливать по коду.

Нужен способ фиксировать решения так, чтобы к ним можно было вернуться.

## Движущие факторы

- Решение, причина которого утеряна, обходят вместо того, чтобы менять
- `C-04`: команда из одного человека — решения некому передать голосом,
  единственный канал — письменный
- Защита проекта (ЛР 9Б) требует обоснований принятых решений
- Записи должны лежать там же, где код: отдельное хранилище документов
  расходится с системой в первую же неделю

## Рассмотренные варианты

| Вариант | За | Против |
| --- | --- | --- |
| **Записи в репозитории по формату MADR** | Рядом с кодом; проходят саморевью по DoD; история в Git; ссылка из кода и запросов на слияние | Нужна дисциплина: запись придётся писать |
| Раздел в общем документе требований | Одно место | Решения тонут среди требований; история изменений нечитаема |
| Записи в Jira | Привязка к задачам | Отрываются от кода; живут в отдельном сервисе с ограниченным сроком |
| Не фиксировать | Ничего не нужно делать | Текущее положение, которое и привело к проблеме |

## Решение

Записи в репозитории, в каталоге `docs/adr/`, по формату **MADR**.

Правила:

1. **Одно решение — один файл.** Имя: `NNNN-kebab-case-title.md`, номер
   четырёхзначный, по порядку, **не переиспользуется**.
2. **Записи не правят и не удаляют.** Изменилось решение — статус старой
   меняется на «заменено на ADR-NNNN», пишется новая.
3. **Запись нужна решению, которое затрагивает несколько частей системы,
   трудно обратимо либо влияет на атрибуты качества.** Остальное решается
   в коде и в саморевью.
4. **Обязательные разделы**: статус, дата, участники, контекст, движущие
   факторы, рассмотренные варианты (не менее двух), решение с определяющим
   доводом, последствия с отрицательной частью и условием пересмотра.
5. **Решение принимает команда** (здесь — один участник), а на защите
   объясняет его по записи. Саморевью записи — до слияния, по DoD
   из [../process.md](../process.md).
6. **Указатель** `docs/adr/README.md` обновляется в том же запросе.

## Последствия

**Положительные.** Причина решения доступна через месяцы. Спор, разобранный
один раз, не повторяется. Защита опирается на записи, а не на память.

**Отрицательные.** Запись требует времени: от двадцати минут до часа. Есть
риск формальных записей, написанных ради наличия, — он уменьшается
требованием раздела альтернатив с реальными доводами. В одиночном проекте
некому указать на пропущенный довод — компенсация саморевью с перерывом.

**Что пересмотрит решение.** Появление в вузе единого требования
к оформлению проектной документации, несовместимого с этой формой.
