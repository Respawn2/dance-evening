# Агрегаты

Границы согласованности системы. Ссылки между агрегатами — по идентификатору;
одна транзакция меняет один агрегат. Инварианты пронумерованы сквозно (И-1…И-16)
и используются в модели данных (ЛР 2Г) и тестах (ЛР 5).

## Вечер (Evening) — основной агрегат

**Корень**: `Evening` · **Контекст**: Вечера и записи

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Evening` | Сущность, корень | Имеет тождество: «какой именно вечер» — осмысленный вопрос |
| `EveningCategory` | Значение (перечисление) | `dance` / `standup` / `quiz` / `concert` / `games`; определяет, нужны ли роли в паре и выравнивание цены |
| `Venue` | Значение | Название и адрес; «какое именно „Бар, Ленина 12“» — вопрос без смысла, сравнивается содержимым |
| `TimeRange` | Значение | Полуоткрытый интервал `[начало, окончание)`; соприкасающиеся вечера организатора пересечением не считаются (`AC-03.6`) |
| `Capacity` | Значение | Лимит мест: положительное целое |
| `PricePolicy` | Значение | Базовые цены ролей в паре, порог перекоса, предел снижения; задаётся организатором при публикации (`AC-03.7`) |
| `Price` | Значение | Неотрицательная сумма в рублях; отдельного контекста расчётов нет (`FR-16` вне охвата) |
| `EveningStatus` | Значение (перечисление) | Хранятся `announced` / `cancelled`; `ongoing` / `finished` вычисляются при чтении сравнением с текущим временем (события 12, 15 сессии) |

### Инварианты

| № | Инвариант | Почему инвариант, а не правило сценария |
| --- | --- | --- |
| И-1 | Интервал вечера положителен: `ends_at > starts_at` | Проверяется по данным самого агрегата |
| И-2 | Длительность — от 30 минут до 12 часов | По данным агрегата (`AC-03.3`) |
| И-3 | Лимит мест положителен | По данным агрегата |
| И-4 | У танцевального вечера политика цен полная: обе цены ролей и порог перекоса | По данным агрегата (`AC-03.7`) |
| И-5 | Цены неотрицательны; предел снижения в интервале (0, 100] | По данным агрегата |
| И-6 | Отменённый вечер нельзя изменить или отменить повторно | По состоянию агрегата |
| И-7 | Название и заведение непусты | По данным агрегата |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
| --- | --- | --- |
| Вечер не в прошлом | Нужно текущее время — внешняя зависимость | Сценарий публикации с часами из `ports/clock.py` (`AC-03.2`) |
| Вечера одного организатора не пересекаются | Нужны другие вечера — другие экземпляры агрегата | Сценарий + ограничение исключения в базе (ЛР 4А, `AC-03.6`) |
| Лимит не исчерпан | Нужны записи — другой агрегат | Сценарий записи (`AC-04.2`), от состязания защищает база |
| Организатор существует | Другой контекст | Сценарий: проверка идентификатора и роли |

### События

| Событие | Когда | Что несёт |
| --- | --- | --- |
| `EveningPublished` | Вечер опубликован | `evening_id`, категория, заведение, интервал, лимит, политика цен |
| `EveningChanged` | Изменения сохранены | `evening_id`, что изменилось |
| `EveningCancelled` | Вечер отменён | `evening_id`, причина, кто отменил |

`EveningStarted` и `EveningFinished` не публикуются агрегатом: они вычисляются
при чтении (раздел «События без команды» в
[event-storming.md](event-storming.md)).

### Границы и ссылки

- Ссылка на организатора — по идентификатору `organizer_id`, другой контекст
- Записи ссылаются на вечер по `evening_id`, вечер о записях не знает
- Одна транзакция меняет один агрегат: публикация и отмена вечера не трогают
  записи

### Почему записи не внутри агрегата «Вечер»

Первое побуждение — сделать запись частью вечера: тогда лимит становится
инвариантом, и отмена вечера согласованно меняет все записи. Цена: на вечер
со ста записями сто посетителей не могут записаться одновременно — каждый
запрос перезагружает и блокирует весь агрегат, «одна транзакция — один
агрегат» превращается в очередь за одним вечером.

Решение: записи — отдельный агрегат; лимит проверяется сценарием с обращением
к хранилищу, от состязания двух запросов на последнее место защищает база
(`AC-04.3`, ЛР 4А). Отмена вечера не меняет записи транзакционно:
недействительность записей вычисляется при чтении статуса вечера (`AC-22.2`,
вопрос В-1 сессии). Цена решения — согласованность вечера и счётчиков
состава в конечном итоге, а не в транзакции; для продукта это принято
(«Кто идёт» обновляется не позднее 5 секунд, `ADR-0005`).

## Запись (Registration)

**Корень**: `Registration` · **Контекст**: Вечера и записи

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Registration` | Сущность, корень | Имеет тождество: «какая именно запись» — осмысленный вопрос |
| `DanceRole` | Значение (перечисление) | `leader` / `follower` для танцевальных, `none` для остальных; «какая именно роль „ведомая“» — вопрос без смысла |
| `RegistrationStatus` | Значение (перечисление) | `active` / `confirmed` / `cancelled` / `withdrawn` / `arrived` / `no_show`; «вечер отменён» — не статус записи: вычисляется по вечеру |
| `Withdrawal` | Значение | Причина и момент; обязательна при снятии (вопрос В-2 сессии) |

### Инварианты

| № | Инвариант | Почему инвариант, а не правило сценария |
| --- | --- | --- |
| И-8 | Если категория вечера танцевальная, роль в паре задана; категория передаётся при создании | Категория — параметр создания, как вместимость в брони; данных других агрегатов в рантайме не нужно (`AC-04.5`) |
| И-9 | У снятой записи указаны причина и автор | По данным агрегата (`AC-21.2`) |
| И-10 | Отменённую или снятую запись нельзя отменить или снять повторно | По состоянию агрегата (`AC-05.4`, `AC-21.4`) |
| И-11 | `arrived` и `no_show` взаимоисключающи и недоступны для отменённой и снятой записи | По состоянию агрегата (`AC-08.4`, `AC-08.5`) |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
| --- | --- | --- |
| Посетитель не записан на вечер повторно | Нужны другие записи — другие экземпляры агрегата | Сценарий + ограничение уникальности в базе (ЛР 4А, `AC-04.4`) |
| Лимит вечера не исчерпан | Нужен агрегат «Вечер» и другие записи | Сценарий записи (`AC-04.2`, `AC-04.3`) |
| Вечер не начался и не отменён | Другой агрегат плюс текущее время | Сценарий с часами (`AC-04.6`, `AC-05.2`) |
| Срок подтверждения истёк | Нужен момент начала вечера и текущее время | Вычисляется при чтении (`AC-12.3`) |

### События

| Событие | Когда | Что несёт |
| --- | --- | --- |
| `RegistrationCreated` | Запись создана | `registration_id`, `evening_id`, `user_id`, роль в паре |
| `RegistrationConfirmed` | Явка подтверждена (RSVP) | `registration_id`, момент |
| `RegistrationCancelled` | Отменена посетителем | `registration_id`, момент |
| `RegistrationWithdrawn` | Снята организатором | `registration_id`, причина, кто снял |
| `VisitorArrived` | Отмечен приход | `registration_id`, момент |
| `VisitorMarkedNoShow` | Зафиксирована неявка | `registration_id`, момент |

### Границы и ссылки

- Ссылка на вечер — по идентификатору `evening_id`, не объектом
- Ссылка на пользователя — по идентификатору `user_id`, другой контекст
- Отзыв ссылается на запись из своего контекста; запись об отзывах не знает

## Отзыв (Review)

**Корень**: `Review` · **Контекст**: Отзывы и репутация

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Review` | Сущность, корень | Имеет тождество: «какой именно отзыв» |
| `Rating` | Значение | Целое 1–5; две пятёрки — одна и та же оценка |
| `ReviewText` | Значение | Текст до 2 000 символов; изменение отзыва — новое значение, а не правка старого |

### Инварианты

| № | Инвариант | Почему инвариант, а не правило сценария |
| --- | --- | --- |
| И-12 | Оценка — целое от 1 до 5 | По данным агрегата (`AC-09.4`) |
| И-13 | Текст непустой и не длиннее 2 000 символов | По данным агрегата |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
| --- | --- | --- |
| Один отзыв на вечер от одного пользователя | Нужны другие отзывы | Сценарий + ограничение уникальности в базе (`AC-09.5`) |
| Только от отметившихся приход | Нужна запись — другой контекст | Сценарий: проверка факта прихода при создании отзыва (`AC-09.2`) |
| Вечер завершён | Нужен агрегат «Вечер» и время | Сценарий (`AC-09.3`) |

### События

| Событие | Когда | Что несёт |
| --- | --- | --- |
| `ReviewPublished` | Отзыв опубликован | `review_id`, `evening_id`, `user_id`, оценка |

### Границы и ссылки

- Ссылки на вечер и пользователя — по идентификаторам
- Связь с контекстом «Вечера и записи» — поставщик — потребитель: контекст
  отзывов получает список отметившихся и не знает про записи и лимиты

### Почему право отзыва — не инвариант

Правило «только от отметившихся» требует данных другого контекста — факта
прихода из записи. Попытка выразить его инвариантом затащила бы записи внутрь
агрегата отзыва и связала бы два контекста, которые меняются по разным
правилам. Поэтому это правило сценария: при создании отзыва сценарий
обращается к списку отметившихся — ровно та связь, что на карте контекстов
обозначена «поставщик — потребитель».

## Пользователь (User)

**Корень**: `User` · **Контекст**: Учёт участников

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `User` | Сущность, корень | Имеет тождество |
| `Email` | Значение | Проверяется на форму; для входа, публично не показывается |
| `Nickname` | Значение | Публичное имя в блоке «Кто идёт» и отзывах |
| `UserRole` | Значение (перечисление) | `visitor` / `organizer`; это роль пользователя, не роль в паре (расхождение Р-2) |

### Инварианты

| № | Инвариант |
| --- | --- |
| И-14 | Адрес электронной почты уникален — проверяется ограничением в базе (ЛР 4А) |
| И-15 | Роль пользователя — одно из двух допустимых значений |
| И-16 | Публичный ник непуст |

### Границы

Контекст «Учёт участников» не знает о вечерах, записях и отзывах. Связь
односторонняя: «Вечера и записи» и «Отзывы» ссылаются на пользователя
по идентификатору. Это связь «поставщик — потребитель»: при изменении модели
пользователя учитываются потребности записи и отзыва.
