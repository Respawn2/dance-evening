# Рефакторинг модуля 08

Отчёт о переработке обработчика записи: что было найдено, почему это проблема,
что сделано и что изменилось. Поведение системы к концу работы то же, что
в начале, — это подтверждено тестами, написанными до изменений.

Обработчик `create_registration` в `src/evenings/api/registrations.py`,
написанный «как написал бы любой»: разбор словаря, пять проверок подряд,
глобальные словари-хранилища, `datetime.now()` и `uuid4()` в теле,

## Что нельзя проверить сейчас

| Что | Почему |
| --- | --- |
| Границу правила «вечер не начался» | Время берётся из системных часов (`datetime.now(UTC)`, строки 77 и 106); «вечер начался минуту назад / начнётся через минуту» задать нечем |
| Совпадение идентификатора в ответе и в хранилище | `uuid.uuid4()` в строке 99 непредсказуем; тест может утверждать только непустоту |
| Конфликт повторной записи при известном исходном состоянии | Хранилища глобальны (строки 13 и 43), состояние тянется между тестами; порядок запуска влияет на результат |
| Факт отправки подтверждения | Письмо уходит по-настоящему (`smtplib.SMTP`, строка 119); при недоступном сервере ошибка проглатывается `except OSError: pass` (строка 121) — в журнале не остаётся ничего |

Проверка «тесты действительно проверяют»: замена `>=` на `>` в проверке лимита
сделала тест `test_capacity_is_enforced` красным; после возврата проверки —
зелёным. Тесты защищают поведение, а не присутствуют.

## Аудит тестируемости

### Т-1. Текущее время

**Где**: `api/registrations.py`, строки 77 и 106 — `datetime.now(UTC)` в правиле
«вечер не начался» и в `created_at`

**Почему нельзя проверить**: поведение на границе («запись за минуту до начала
доступна, с момента начала — нет», `AC-04.6` и `AC-05.2`) зависит от момента
запуска теста. Задать «сейчас» нечем.

**Шов**: интерфейс `Clock` с методом `now()`, передаётся в сервис аргументом
конструктора. В тесте — `FixedClock`.

### Т-2. Порождение идентификатора

**Где**: `api/registrations.py`, строка 99 — `registration_id = str(uuid.uuid4())`

**Почему нельзя проверить**: идентификатор в ответе непредсказуем; проверить,
что в хранилище и в ответе один и тот же идентификатор, нельзя.

**Шов**: интерфейс `IdGenerator`. В тесте — `SequentialIds` (`r-1`, `r-2`, …).

### Т-3. Хранилище

**Где**: `api/registrations.py`, строки 13 и 43 — `_EVENINGS: dict[str, dict]`
и `_REGISTRATIONS: dict[str, dict]` на уровне модуля

**Почему нельзя проверить**: состояние глобально и живёт между тестами; задать
исходное состояние для теста нельзя — только создать его запросами.

**Шов**: интерфейсы `EveningRepository` и `RegistrationRepository` (агрегаты
разделены, поэтому порта два). В тесте — поддельные реализации в памяти,
создаваемые на каждый тест заново.

### Т-4. Оповещение

**Где**: `api/registrations.py`, строки 108–122 — письмо собирается в обработчике,
адрес получателя домысливается склейкой `f"{user_id}@example.com"` (строка 113),
отправка через `smtplib.SMTP` (строка 119), отказ проглатывается без записи
в журнал (строка 121)

**Почему нельзя проверить**: побочное действие происходит по-настоящему;
утверждение «при отказе канала запись остаётся действующей» (`AC-10.2`)
написать нельзя — отказа не видно вовсе.

**Шов**: интерфейс `Notifier` с методом `registration_created` — назван по
событию, не `send(text)`: сервис сообщает факт, а не собирает письмо (уровень
предотвращения искажений из ЛР 2Б). В тесте — шпион `SpyNotifier` и подставка
отказа `FailingNotifier`.

вариантов ответа один. Не применяем оба.

## План

1. Выделить типы значений и агрегаты по модели ЛР 2Б (`domain/models.py`)
2. Перенести правила сценария в чистые функции (`domain/rules.py`), ошибки —
   в `domain/errors.py` без кодов HTTP
3. Объявить интерфейсы рядом с потребителем: два хранилища, часы,
   идентификаторы, оповещение (`ports/`)
4. Написать реализации: в памяти, системные часы, журнальное оповещение (`adapters/`)
5. Собрать сценарий `RegistrationService` без знания о HTTP и SQL (`services/`)
6. Свести обработчик к преобразованию HTTP ↔ сценарий (`api/registrations.py`),
   выбор реализаций — в корень композиции (`api/dependencies.py`)
7. Перевести тесты правил на уровень предметной логики, добавить тесты
   сценария на дублях; HTTP-тесты не трогать
8. Применить стратегию для правил по категориям (`services/policies.py`)

Шаги 1–2 первыми: от них зависят подписи всего остального. Шаг 6 последним:
до него обработчику нечего вызывать.

Шпион выбран для оповещения, потому что исходящее действие и есть требование
(`FR-10`): результата нет, проверить можно только факт. Для остальных швов

делаются о результате. Тестов, проверяющих, что подставку спросили, нет.

Дубли написаны руками, не `unittest.mock`: соответствие протоколам проверяет
`mypy`, и переименование метода ломает тест, а не проходит молча.

## Сравнение с вариантом языковой модели

Упражнение выполнено в инвертированной форме: черновик модели дорабатывался
по шагам методички, и расхождения фиксировались по ходу.

1. **Какие швы модель не ввела:** в первом черновике `datetime.now(UTC)`
   остался внутри правила «вечер не начался» — время стало аргументом только
   после аудита Т-1. Типичная слепота из методички: время впаяно незаметно
   для автора кода.
2. **Какие абстракции модель ввела без надобности:** предложен `Notifier`
   сразу с четырьмя методами из расшифровки сессии ЛР 2Б
   (`registration_cancelled`, `evening_published`, …) — отклонено: сценарию
   нужен один метод (разделение интерфейсов); предложен единый репозиторий
   «Вечера и записи» — отклонено: агрегаты разделены (ЛР 2Б); предложено имя
   `RegistrationManager` — запрещено глоссарием.
3. **Что в её варианте лучше:** имена тестов вида
   `test_evening_is_closed_from_the_start_moment` и `ids` параметризации
   (`dance-leader`, `quiz-with-role`) — приняты: имя теста читается как
   утверждение и попало в отчёт без правок.
